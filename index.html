1. What the change does

By default Kubernetes keeps revisionHistoryLimit: 10 old, scaled-to-0 ReplicaSets per Deployment. Each pins a superseded image tag, so old tags linger in runtime image inventories long after they stop running. Setting a small revisionHistoryLimit lets Kubernetes garbage-collect them. The operator sets it in two places:

  • Operator's own Deployment (Helm chart): default revisionHistoryLimit: 2.
  • Operator-managed Deployments (Druid routers): makeDeploymentSpec sets RevisionHistoryLimit (default 2) — the focus of this report.
+ // bound retained ReplicaSets for operator-managed Deployments (e.g. routers)
+ const defaultDeploymentRevisionHistoryLimit int32 = 2

  func makeDeploymentSpec(...) appsv1.DeploymentSpec {
+     revisionHistoryLimit := defaultDeploymentRevisionHistoryLimit
      deploySpec := appsv1.DeploymentSpec{
          Selector:             &metav1.LabelSelector{MatchLabels: ls},
          Replicas:             &nodeSpec.Replicas,
+         RevisionHistoryLimit: &revisionHistoryLimit,
          Template:             makePodTemplate(...),
          Strategy:             appsv1.DeploymentStrategy{Type: "RollingUpdate", ...},
      }
  }
Scope: Deployments only (routers, plus the operator's own Deployment). StatefulSet workloads have no ReplicaSets and are out of scope. revisionHistoryLimit is a freely-mutable Deployment field and is not part of the pod template, so setting it does not by itself trigger a pod rollout.

Note — a MiddleManager-drain edge case had to be cleared first

The operator reconciles Druid nodes sequentially with the router last, and stops at the first node whose rollout is in progress. The MiddleManager rolling-restart wedged the reconcile before it reached the router, due to a drain edge case unrelated to this change:

The MiddleManager drain derives the handoff target from a task's datasource and calls the streaming-supervisor handoff API with that value — i.e. it treats the datasource name as a supervisor id. When a streaming supervisor's id differs from its datasource (e.g. multiple supervisors feeding one shared datasource), the handoff targets a supervisor that does not exist → HTTP 404, which the drain treats as fatal and aborts the whole-cluster reconcile. These tasks are not orphaned — the active supervisors immediately respawn them, so deleting tasks does not durably clear it.
# mm_drain.go — supervisorID is taken from the DATASOURCE, then used as a supervisor id
supervisorID := payload.Payload.DataSource
... triggerTaskGroupHandoff(overlordBaseURL, supervisorID, taskGroupIDs)
if resp.StatusCode != 200 && resp.StatusCode != 202 { return err }   # 404 treated as fatal → aborts reconcile

Unblock: deleting the stuck MiddleManager StatefulSet let the operator recreate it fresh. A freshly created StatefulSet has CurrentRevision == UpdateRevision, so the rollout path logs "already at latest revision, nothing to do" and skips the drain entirely (no handoff, no 404). The reconcile then walked through the nodes to the router and applied revisionHistoryLimit: 2.

Recommended hardening (independent of this change): resolve the true supervisor id rather than using the datasource, and treat a 404 on handoff as skip-and-continue (the drain code already skips gracefully when fetching task payloads). Otherwise a supervisor-id ≠ datasource situation can wedge the whole-cluster reconcile on the next MiddleManager rollout.

4. Conclusion

  • Validated on both surfaces. Local kind: a router kind: Deployment gets revisionHistoryLimit: 2 and holds retained ReplicaSets at 2 (total 3) across 6 rollouts. Shared cluster: an in-place operator upgrade set the live router Deployment to revisionHistoryLimit: 2 and Kubernetes GC'd the stale ReplicaSets from 7 → 3 (5 removed).
  • Safe, allowed update. revisionHistoryLimit is a mutable Deployment field; the operator applies it idempotently (hash-based diff → one update, then it settles). Setting it does not by itself restart pods.
  • Separate finding: the MiddleManager drain can wedge a whole-cluster reconcile when a streaming supervisor's id differs from its datasource (404 on handoff treated as fatal). Worth hardening independently.
